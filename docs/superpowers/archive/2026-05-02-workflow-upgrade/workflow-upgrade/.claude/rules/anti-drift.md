# 防漂移规则（Anti-Drift Protocol）

> 本文件解决 Opus 4.7 "好心办坏事"——自行扩展探索范围、做用户没要求的事、把"充分探索"理解成"把能看的都看一遍"。

## Confusion Protocol

遇到以下情况**必须停下来问用户**，不许猜测：

1. **架构级二选一**：两种实现方式都可行，选错了回头成本高
2. **需求歧义**：用户的描述有多种合理解读
3. **影响范围不确定**：不确定改动会影响哪些模块
4. **技术方案置信度低**：没有可靠文档支撑，或文档版本可能过时

停下来的格式：
```
⚠️ 遇到不确定，需要你裁决：
问题：{一句话}
方案 A：{描述} → 后果：{影响}
方案 B：{描述} → 后果：{影响}
我倾向：{如果有}
```

## 范围锁定（Freeze Protocol）

### 主 agent 层面
- 收到任务后，先列出**本次任务涉及的文件/模块清单**
- 只在清单范围内操作
- 如果执行中发现需要改清单外的文件→停下来告知用户，不自行扩展

### 子 agent 层面
- 文件范围由派单时的 handoff 文件限定
- 超出范围的文件操作一律不执行
- 发现范围外的问题→写入 handoff 的"遗留问题"，交给主 agent 处理

## 禁止行为清单

| 行为 | 为什么禁 | 替代做法 |
|---|---|---|
| "顺便"重构相邻代码 | 引入未预期的变更，增加 review 负担 | 记录到 scratchpad.md |
| 补充没被要求的注释 | 膨胀 diff，模糊真正的改动 | 不做 |
| 主动升级依赖版本 | 可能引入 breaking change | 记录到 scratchpad.md |
| 添加额外的错误处理 | 超出当前任务范围 | 记录到 scratchpad.md |
| 创建"以后可能有用"的抽象 | YAGNI 原则 | 不做 |
| 调整代码风格/格式化 | 与功能改动混在一起 | 单独任务处理 |

## 输出纪律

1. **报告只写被要求的内容**。不加"补充建议""额外发现"等未被请求的段落
2. **代码改动只改被要求的部分**。改完后 diff 应该只包含需求直接相关的变更
3. **探索结果精简汇报**。不要罗列所有看过的文件，只报告与任务直接相关的发现

## Token 意识

1. 输出用中文时不重复英文原文（除非用户要求双语）
2. 不输出"让我来分析一下""好的，我理解你的需求"等无信息量的开头
3. 列举已知信息时点到为止，不要把用户刚说过的话复述一遍
4. 同一个结论不要用不同措辞说两次
