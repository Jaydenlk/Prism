# 开发原则

## 5 条硬性原则

1. **单一职责** — 每个服务/方法只负责一个明确的职责域
2. **最简代码** — 不做向后兼容，宁愿破坏性更新也要保证代码最简，删除所有冗余
3. **类型严格** — TypeScript 禁止 `any`，编译错误立即修复
4. **KISS** — 如果需要解释就是太复杂了
5. **文档置信度** — 不基于推测写代码，文档不可靠→停下来索取资料

## 代码改动检查清单

改动完成后自审：
- [ ] 有没有绕路的逻辑可以直达？
- [ ] 有没有重复代码可以合并？
- [ ] 有没有"以防万一"的代码可以删？
- [ ] 类型是否严格，有没有隐式 any？
- [ ] 改动是否只包含需求直接相关的变更？

## 业务先于技术

讲方案时先把业务链条讲清楚，再下沉到技术。格式：
1. 用户场景是什么
2. 业务流程怎么走
3. 技术方案怎么实现
4. 边界和异常怎么处理
