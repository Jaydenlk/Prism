# PrismV3 AI 开发工作流完整指南

> **用途**：向外部分享本项目的 AI 辅助开发工作流体系
> **版本**：2026-05-17
> **适用场景**：使用 Claude Code（AI 编程助手）进行软件开发的团队

---

## 一、总览：这套工作流解决什么问题

### 背景

当你让 AI 写代码时，最常遇到的问题是：

- AI 自作主张改了你没要求改的东西
- AI 写了一半的代码，留下 TODO 就说"完成了"
- AI 修 bug 靠打补丁绕过，而不是修根本原因
- AI 基于过时的知识写代码，接口已经变了都不知道
- 多个 AI 会话之间信息断裂，前一个会话做的决策后一个完全不知道
- AI 说"测试通过了"，实际上根本没跑测试

### 这套工作流做了什么

我们设计了一套 **完整的 AI 开发治理体系**，让 AI 像一个受过严格训练的开发团队一样工作：

- 有明确的 **团队分工**（谁写代码、谁测试、谁审查）
- 有严格的 **行为准则**（什么能做、什么不能做）
- 有标准的 **工作流程**（从接到任务到交付的每一步）
- 有完善的 **记忆系统**（决策不丢失、经验可传承）
- 有自动的 **质量把关**（写完不是结束，验证通过才是）

## 二、团队：AI 里的专业分工

### 为什么要分工？

一个人既写代码又审查自己的代码，很容易"当局者迷"。我们把 AI 拆成多个角色，每个角色有独立的视角和权限，互相制衡。

### 角色一览

| 角色 | 通俗比喻 | 做什么 | 看得到什么 |
|------|----------|--------|-----------|
| **Coordinator（主管）** | 项目经理 | 拆解任务、分配工作、整合结果、做决策 | 全局视野 |
| **Implementer（工程师）** | 前线开发 | 在隔离环境中写代码 | 只看自己被分配的文件 |
| **Reviewer（审查员）** | 代码审查官 | 只读代码找问题，不能改代码 | 只读权限 |
| **QA Engineer（测试员）** | 质量保证 | 打开真实浏览器像人一样操作测试 | 浏览器 + 只读代码 |
| **Explorer（侦察兵）** | 快速摸底 | 在指定范围内搜索代码结构 | 只读权限 |
| **Decision Recorder（记录员）** | 会议记录 | 记录每个重要决策的"选了什么、为什么排除其他" | 决策记录库 |

### 分工的好处

1. **写代码的人不能审自己的代码** → 避免"自己觉得没问题"的盲区
2. **审查的人不能改代码** → 确保审查意见独立客观，不会"顺手改了算了"
3. **测试的人用真实浏览器** → 不是"理论上应该能跑"，而是"我实际点过每个按钮"
4. **每个人只看自己需要的** → 避免信息过载导致的混乱

## 三、规则体系：13 条行为准则

### 为什么需要规则？

AI 的通病是"太热心"——你让它修一个 bug，它顺手把旁边的代码也"优化"了，结果引入了新问题。这些规则就是给 AI 划定边界。

### 第一类：开发底线（5 条）

| 原则 | 通俗解释 | 避免的问题 |
|------|----------|-----------|
| **单一职责** | 一个模块只干一件事 | 避免"万能函数"——改一处影响十处 |
| **最简代码** | 能删的代码一定删，绝不"留着以后万一有用" | 避免代码越写越臃肿，维护成本指数增长 |
| **类型严格** | 每个变量的类型必须明确，不允许模糊处理 | 避免运行时突然崩溃——"传进来的居然不是数字" |
| **KISS** | 如果需要解释才能看懂，就是太复杂了 | 避免"聪明代码"——作者写的时候得意，别人看不懂 |
| **文档置信度** | 不确定接口怎么用？停下来查官方文档，不猜 | 避免"我记得好像是这样"——结果接口早就改了 |

### 第二类：防漂移规则

**是什么**：防止 AI 在执行任务时偷偷扩大范围。

**具体约束**：
- 开始前先列清单：这次要改哪些文件
- 只在清单内操作，想改别的？先征求同意
- 禁止"顺便重构"、"顺便加注释"、"顺便升级依赖"
- 发现了别的问题？记下来另开任务，这次不碰

**避免的问题**：一个小修复变成了大重构，review 时根本分不清哪些是真正的修改、哪些是"顺手优化"。

### 第三类：防摸鱼规则

**是什么**：防止 AI 敷衍了事。

**具体约束**：
- 不允许说"测试通过了"却不附证据（必须贴实际输出）
- 不允许代码里留 `TODO` 或 `// 以后实现`
- 不允许说"探索了但没发现"——必须展示搜索过程
- 卡住超过 8 轮循环？停下来汇报，不要无意义重试

**避免的问题**：AI 声称完成了但实际上是"半成品"，或者在同一个错误上无限循环浪费时间。

### 第四类：研究路由规则

**是什么**：规定 AI 在需要查资料时，应该去哪里查、怎么查。

| 要查什么 | 去哪查 | 为什么 |
|----------|--------|--------|
| 某个库的 API 怎么用 | Context7（实时文档查询） | 训练数据可能过时，API 可能已经变了 |
| 最新的最佳实践 | Exa（AI 语义搜索） | 技术趋势变化快，6 个月前的建议可能已过时 |
| 同类产品怎么做的 | Web 搜索 + 深度阅读 | 避免闭门造车，参考业界做法 |
| 团队之前的经验 | mem0（记忆库） | 不要重复犯团队已经踩过的坑 |

**避免的问题**：AI 凭"记忆"写代码，用了已经废弃的 API，或者提出一个业界早已淘汰的方案。

### 第五类：Karpathy 四原则

来源是 AI 领域知名研究者 Andrej Karpathy 的编程哲学：

1. **想清楚再动手** — 不确定就问，不要默默猜
2. **简单至上** — 200 行能缩到 50 行？重写
3. **外科手术式改动** — 每一行改动都必须能追溯到用户的要求
4. **目标驱动** — "修好了"不是目标，"这个测试用例通过"才是

### 第六类：验收标准

**前端验收**：
- 用 Playwright（浏览器自动化工具）实际操作
- 桌面端（大屏）+ 手机端（小屏）都要测
- 每个按钮点一遍，每个输入框填一遍
- 不只看"页面显示正常"，还要验证"数据确实保存了"

**后端验收**：
- 正常情况的测试（该成功的成功）
- 异常情况的测试（该失败的正确失败）
- AI 相关接口：设计刁钻的测试场景，不只跑"最简单的情况"

## 四、流程：一个任务从开始到完成的全过程

### 概览图

```
接到任务
  ↓
头脑风暴（brainstorming）— 想清楚要做什么、怎么做
  ↓
写计划（writing-plans）— 列出每一步和验证方法
  ↓
创建隔离环境（git worktree）— 在独立空间里开发，不影响主代码
  ↓
先写测试（TDD）— 先定义"成功长什么样"
  ↓
写代码实现
  ↓
逐步验证 — 每写一步就验证一步，不是写完再说
  ↓
简化审查（simplify）— 三个 AI 并行检查：能复用吗？质量够吗？效率高吗？
  ↓
项目审查（PJR）— 代码规范、构建通过、逻辑正确
  ↓
代码审查（code review）— 独立审查员找问题
  ↓
端到端测试 — 真实浏览器走完整流程
  ↓
提交 + 更新进度记录
```

### 阶段详解

#### 阶段 1：头脑风暴（Brainstorming）

**是什么**：开工前的思考阶段，确保理解清楚需求。

**做什么**：
- 查看当前代码状态
- 提出 2-3 种实现方案
- 分析每种方案的优缺点
- 确认方案后记录决策

**为什么不直接写代码**：避免"写了一半发现方向错了"，越早发现问题修正成本越低。

#### 阶段 2：写计划（Writing Plans）

**是什么**：把想法变成可执行的步骤清单。

**格式要求**（step→verify）：
```
1. 创建用户注册接口 → 验证：发送注册请求，返回 201 + 用户 ID
2. 添加邮箱重复检查 → 验证：用已有邮箱注册，返回 409 冲突
3. 添加密码强度校验 → 验证：弱密码注册，返回 400 + 错误提示
```

**为什么每步都要有验证方法**：避免"做完了但不确定对不对"——每一步的成功标准在动手之前就定好了。

#### 阶段 3：隔离开发（Git Worktree）

**是什么**：在主代码库旁边开辟一个独立的工作空间。

**通俗比喻**：就像画家在草稿纸上画，满意了再贴到正式画布上。

**为什么要隔离**：
- 实验性的改动不会影响正在运行的系统
- 出了问题直接丢掉草稿，主代码完好无损
- 多个任务可以同时进行互不干扰

#### 阶段 4：测试驱动开发（TDD）

**是什么**：先写"判断标准"，再写实现。

**通俗比喻**：考试前先出考卷（测试），再让学生答题（写代码）。如果连题都出不好，说明需求还没想清楚。

**为什么先写测试**：
- 逼你把需求想具体（"输入什么，应该输出什么"）
- 写完代码后有自动判断对错的方法
- 修改代码时能立刻知道有没有改坏别的功能

#### 阶段 5：简化审查（Simplify）

**是什么**：三个 AI 并行检查代码质量。

| 检查员 | 看什么 | 发现什么 |
|--------|--------|----------|
| Reuse（复用） | 有没有重复的代码可以合并？ | "这段逻辑和那个文件里的一样" |
| Quality（质量） | 代码有没有隐患？ | "这里没处理空值" |
| Efficiency（效率） | 有没有明显低效的写法？ | "这个循环里重复查了数据库" |

**为什么三个并行**：每个检查员只关注一个维度，不会互相干扰，且速度快。

#### 阶段 6：端到端测试

**是什么**：像真人一样操作浏览器走完整个业务流程。

**具体做法**：
- 打开浏览器，进入页面
- 点击注册按钮
- 填写表单
- 提交
- 验证跳转到了正确页面
- 验证数据确实保存了
- 切换到手机屏幕尺寸再走一遍

**为什么不只跑单元测试**：单元测试检查"零件是否合格"，端到端测试检查"整辆车能不能开"。

## 五、通信机制：AI 之间怎么传递信息

### 为什么不能直接对话？

AI 助手每次对话都有"记忆容量"限制。如果所有信息都塞在一个对话里，很快就会"装不下"，开始遗忘早期内容。

### 解决方案：文件状态机

**通俗比喻**：就像工厂的工单系统——工人 A 完成自己的部分，在工单上签字并写下注意事项，交给工人 B 继续。

**流转状态**：
```
准备开发 → 准备审查 → 准备测试 → 完成
```

**工单格式**（Handoff 文件）：
```
工单：A 交给 B

任务：一句话描述要做什么
需要看的文件：列表
不许碰的文件：列表
执行步骤：每步 + 验证方法
已完成的：列表
产出物：文件路径 + 简要说明
遗留问题：如有
相关决策：之前做过的相关决定
```

### 五字段派单规则

主管分配任务时**必须**提供：

1. **任务描述** — 一句话说清楚做什么
2. **输入范围** — 只列需要看的文件（不多给）
3. **禁止范围** — 明确不许碰什么（防止越界）
4. **产出预期** — 期望交付什么、放在哪
5. **决策上下文** — 之前做过什么相关决定（避免推翻旧决策）

**为什么这么严格**：避免 AI 拿到任务后"自由发挥"，跑去改了一堆不相关的东西。

## 六、记忆系统：决策不丢失

### 问题：AI 的"金鱼记忆"

每次新对话，AI 都是"失忆"状态。昨天讨论了一小时决定用方案 A，今天新开对话它可能又推荐方案 B。

### 三层记忆架构

| 层级 | 存在哪 | 记什么 | 寿命 |
|------|--------|--------|------|
| **云端记忆（mem0）** | 云服务 | 用户偏好、产品愿景、长期反馈 | 永久 |
| **项目决策台账** | 项目根目录文件 | 每个技术决策：选了什么、排除了什么、为什么 | 项目生命周期 |
| **会话内决策** | .claude/memory/ | 当前任务的即时决策 | 任务生命周期 |

### 什么时候记录决策？

以下 7 个节点**必须**记录（跳过视为违规）：

1. 头脑风暴选定了方案 → 记录选了什么、放弃了什么、权衡点
2. 不同意用户的方案 → 必须给出证据，不能只说"我觉得"
3. 确定了 bug 修复策略 → 记录为什么用这个修法
4. 选了某个技术工具 → 记录为什么用它而不用另一个
5. 改变了架构设计 → 完整记录
6. 发现已有方案 → 记录发现时间（避免重复劳动）
7. 推翻之前的决定 → 必须完整记录新旧方案对比

### 跨会话交接

每个 AI 会话结束时，必须写一份"交接记录"：

- 这次做了什么
- 做到哪一步了
- 下一个会话需要注意什么
- 有什么遗留风险

**为什么**：确保换一个 AI 会话接手时，不会"从零开始"或重复已解决的问题。

## 七、Skills 系统：专业化能力模块

### 是什么

Skills 是预定义的"操作手册"，告诉 AI 在特定场景下该遵循什么流程。就像医院的标准操作规程（SOP）——不同病情走不同的诊疗流程。

### 核心 Skills 一览

| Skill 名称 | 触发场景 | 做什么 |
|------------|----------|--------|
| **brainstorming** | 新功能、新需求 | 引导 AI 先想后做，避免盲目开发 |
| **writing-plans** | 多步骤任务 | 强制产出 step→verify 格式的计划 |
| **test-driven-development** | 写代码 | 强制先写测试再实现 |
| **systematic-debugging** | 遇到 bug | 强制先定位根因，禁止直接"试着修" |
| **using-git-worktrees** | 开始开发 | 强制在隔离环境中工作 |
| **verification-before-completion** | 即将完成 | 强制跑十项质量检查 |
| **requesting-code-review** | 代码写完 | 触发独立审查流程 |
| **simplify** | 审查阶段 | 三个并行检查员审查代码质量 |

### 前端专属 Skills

| Skill 名称 | 做什么 |
|------------|--------|
| **frontend-design** | 确保 UI 有独特设计感，不是 AI 通用风格 |
| **ui-ux-pro-max** | 机构级设计标准：字体、间距、阴影、动画 |

### Skill 加载硬规则

```
创意/新功能 → 必须加载 brainstorming
写代码     → 必须加载 TDD + worktree
调试       → 必须加载 systematic-debugging（根因没找到不许修）
完工       → 必须加载 simplify → PJR → code-review
前端改动   → 额外加载 frontend-design + ui-ux-pro-max
```

**如果 Skill 加载失败？立即停止，通知用户。绝不"没有流程也照做"。**

## 八、安全网：防止各种事故

### 反打补丁规则

**问题**：AI 修 bug 时最常犯的错——加一个 `if` 判断绕过问题，而不是修复根本原因。

**规则**：
- 发现 bug → 必须先追踪根因（数据从哪来？哪一步出错？）
- 根因没找到之前，**不允许提出修复方案**
- 最终修复必须"融入"现有逻辑，不允许"贴一层创可贴"

**通俗比喻**：水管漏水，正确做法是找到漏点修补管道，而不是在下面放个桶接水。

### 文档置信度规则

**问题**：AI 凭"我记得"写代码，但它的"记忆"可能是一年前的。

**规则**：
- 涉及支付、数据库、API 接口、加密等关键功能
- 如果不确定官方文档怎么说 → **停下来**
- 必须去查一手资料（官方文档），不靠二手信息
- 查不到可靠资料 → 写 blocker 报告，等用户提供

**避免**：用了已废弃的 API、签名算法搞错、支付接口参数传错导致资金问题。

### 三密钥独立规则

**问题**：系统中的多个"密码"如果共用一个，一个泄露全部沦陷。

**规则**：
- JWT 密钥（用户登录凭证） — 独立
- 加密密钥（数据加密） — 独立
- 回调密钥（服务间通信） — 独立
- 系统启动时自动检查：三个密钥是否各不相同

### 进程隔离规则

**问题**：如果 AI 执行器出了问题（比如用户写了恶意代码让 AI 跑），不能影响到主系统。

**规则**：
- 主系统（Web 服务）和 AI 执行器（跑用户任务的进程）**完全隔离**
- 它们只通过消息队列和数据库通信
- AI 执行器不能直接读写主系统的内存或文件

**通俗比喻**：主系统是银行柜台，AI 执行器是隔离的审查室。审查室里发生什么都不会影响柜台的正常运营。

## 九、质量门：完成的标准

任务不是"代码写完了"就算完成。必须过以下十项检查：

| # | 检查项 | 通俗解释 |
|---|--------|----------|
| 1 | 所有要求的文件都创建了 | 没有遗漏 |
| 2 | 验证步骤全部通过 | 每一步的预期结果都对了 |
| 3 | 没有 TODO / FIXME | 没有"以后再说"的占位符 |
| 4 | 关键操作有日志 | 出了问题能查到哪里出的 |
| 5 | 业务指标有监控 | 能知道"这个功能每天被用了多少次" |
| 6 | 跨服务调用有追踪 | 一个请求经过多个服务时能串起来看 |
| 7 | 密钥使用正确 | 没有混用三把钥匙 |
| 8 | 数据库变更有迁移脚本 | 改了表结构有正式的升级路径 |
| 9 | 进度记录已更新 | 下一个人能看到当前状态 |
| 10 | 提交信息规范 | 能从 git 历史看懂每次改了什么 |

## 十、实际效果：这套体系带来了什么

### 解决的核心问题

| 问题 | 传统 AI 协作 | 本工作流 |
|------|-------------|---------|
| AI 自作主张 | 经常"顺便优化" | 范围锁定 + 防漂移规则 |
| 半成品交付 | TODO 满天飞 | 防摸鱼规则 + 质量门 |
| 打补丁式修复 | if 套 if 绕过 | 反打补丁规则 + 根因优先 |
| 知识过时 | 用废弃 API | 文档置信度 + 研究路由 |
| 信息断裂 | 新会话重来 | 三层记忆 + 交接记录 |
| 只说不验 | "应该没问题" | E2E 真实测试 + 证据贴出 |
| 审查形同虚设 | 自审自通过 | 角色分离 + 只读审查 |

### 关键设计理念

1. **信任但验证** — AI 的产出必须有可验证的证据
2. **角色制衡** — 写代码、审代码、测代码的不是同一个"人"
3. **最小权限** — 每个角色只看到自己需要的信息
4. **决策可追溯** — 每个选择都有记录，以后能回溯"为什么这样做"
5. **失败升级** — 卡住了不无限重试，有明确的升级路径（自修→AI 升级→人工介入）

### 激活方式

这套体系通过 Claude Code 的以下机制自动生效：

1. **CLAUDE.md** — 项目根目录的配置文件，AI 启动时自动加载
2. **.claude/rules/** — 按需自动加载的规则（触及相关文件时激活）
3. **.claude/agents/** — 子 agent 的预设定义（被主管调度时激活）
4. **Skills 系统** — 通过 Skill 工具按场景触发

不需要用户每次手动配置，放在项目里就会自动生效。

## 十二、适用场景与局限

### 适合

- 中大型项目（多模块、多人协作）
- 对代码质量有严格要求的团队
- 需要 AI 长期维护同一个项目（决策需要传承）
- 涉及支付、认证等高敏感度业务

### 注意事项

- 小型一次性脚本可能不需要这么重的流程
- 需要 Claude Code 作为 AI 开发工具（这套体系为其设计）
- 初始配置有学习曲线，但配好后自动运行
- Skills 系统需要安装对应的插件包
